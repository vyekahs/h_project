## Design Specificity Verdict

이번 라운드는 4건 모두 실측을 통과했고, 특히 `--status-danger-bg` 토큰 설계와 피드백 실패 복구 흐름은 "일단 동작하게"를 넘어 실패 상황 자체를 설계한 흔적이 있습니다. 하지만 화면 전체로 보면 여전히 표준 카드/탭/모달 조합이며, 이 제품의 핵심 가치인 시인성이나 동아리 특유의 정서를 드러내는 고유한 시각 결정은 이번에도 늘지 않았습니다. "제네릭한 Operate 화면"이라는 평가는 유지되지만, 그 안에서의 마감 품질(엣지 케이스, 토큰 설계)은 라운드를 거듭하며 확실히 좋아지고 있습니다.

**디텍터 스캔**: CLI 1건(`side-tab`) — 5라운드 연속 동일 판정으로 허위양성 확정. 라이브 오버레이(4탭×2뷰포트×2테마, 16개 조합) 신규 스캔: `text-occlusion`은 4라운드째와 같은 도구 자기참조 아티팩트(라벨 텍스트가 문자 그대로 "low contrast text"), `gpt-thin-border-wide-shadow`(하단 nav)·`overused-font`(body)는 mypage 파일 범위 밖 공유 요소. **신규 항목 1건**: 다크 테마에서 `.empty-state-small`/`.empty-titles`(데이터 없음 안내 문구)가 `--text-muted` 색상으로 3.56:1 — AA 미달. 이번 라운드 변경사항과는 무관해 보이나(사전부터 있었을 가능성), 처음으로 잡힌 만큼 보고합니다.

**`--color-red-dark` 배경 사용처 전수 조사**: 홈페이지(`+page.svelte:3816,3825`) `.btn-danger` 한 곳 발견. 다만 텍스트 색도 `var(--bg-primary)`로 테마에 맞춰 같이 뒤집혀서(라이트 4.98:1, 다크 6.23:1) 현재는 우연히 안전합니다 — `--bg-primary`가 나중에 다른 다크 회색으로 조정되면 이번에 마이페이지에서 고친 것과 똑같은 앨리어싱 버그가 재발할 수 있는 설계상 취약점입니다.

## Overall Impression

**5라운드 만에 처음으로, 이번 라운드가 지정한 4개 수정 자체는 전부 라이브로 완전히 검증됐습니다.** 대비(양쪽 테마), 드롭다운 클릭-닫힘, 멤버 목록 기본 접힘, 피드백 실패 복구 — 모두 코드 설명과 실제 동작이 정확히 일치했습니다. 다만 그 4개 중 하나(멤버 목록 접힘)가 "+N명 더 보기" 버튼이 클릭 후 DOM에서 사라지는 부수효과로 포커스를 모달 밖으로 흘려보내, 3라운드에서 고쳤던 바로 그 focus trap을 다시 깨뜨렸습니다. 그리고 게임 드롭다운의 "안 닫힘" 문제는 마우스 클릭-어웨이만 고쳐졌을 뿐 Tab 키 경로는 그대로입니다. 5라운드 연속 "고친 자리 옆에서 새 문제가 나오는" 패턴이 이번엔 완전히 끊기지는 않았지만, 지정된 수정 자체의 신뢰도는 이번이 확실히 가장 높았습니다.

## What's Working

1. **멤버 기본 노출 축소가 실측으로 완전히 검증됨.** 6명 중 1명만 뜨고 "+5명 더 보기"가 정확한 숫자를 표시하며, 클릭 시 전체 노출, 재오픈 시 다시 리셋 — 코드와 동작이 완벽히 일치. 3라운드 연속 "고쳤다고 했는데 사실 no-op"였던 자리라 이건 진짜 성과입니다.
2. **`--status-danger-bg` 토큰 설계가 근본 원인을 짚었습니다.** "흰 텍스트를 얹는 배경 전용"이라는 용도를 코드 주석으로 명시하고 별도 토큰을 신설, 실측 대비 라이트 4.98:1·다크 5.62:1로 AA를 여유 있게 통과합니다.
3. **피드백 실패 복구 흐름이 처음부터 끝까지 정직하게 동작합니다.** 강제로 500을 유발해도 성공 모달 철회→입력값 복원→인라인 에러까지 스크립트 그대로 재현됐습니다.

## Priority Issues

**[P1] "+N명 더 보기" 클릭 후 focus trap이 완전히 깨짐 — 이번 라운드 자체가 만든 신규 회귀**
- **왜 문제인가**: "더 보기" 버튼이 클릭되면 `showAllPartyMembers = true`가 되면서 그 버튼 자체가 DOM에서 제거됩니다. 버튼에 있던 포커스가 갈 곳을 잃고 `<body>`로 빠지는데, `trapFocus`의 keydown 리스너는 모달 노드 자체에만 걸려 있어 포커스가 모달 밖으로 나간 순간부터 Escape가 전혀 먹지 않습니다(라이브 재현: 더 보기 클릭 → Escape → 모달이 안 닫힘). 배경 클릭이나 취소 버튼으로는 여전히 닫히므로 마우스 사용자는 못 느끼지만, 정확히 3라운드에서 고쳤던 그 접근성 기능이 4라운드 뒤에 다시 깨진 셈입니다.
- **Fix**: 버튼 클릭 핸들러에서 `showAllPartyMembers = true`로 값을 바꾸기 직전에, 포커스를 모달 내부의 다른 안전한 요소(예: 목록의 첫 체크박스, 또는 `.member-select-list` 컨테이너에 `tabindex="-1"`을 주고 그쪽)로 명시적으로 옮기는 한 줄을 추가.
- **Command**: `$impeccable harden`

**[P1] 게임 검색 드롭다운, Tab 키로는 여전히 안 닫힘 — 마우스만 고쳐진 절반짜리 수정**
- **왜 문제인가**: 이번 라운드가 고친 건 "클릭으로 다른 필드를 눌렀을 때"뿐입니다. Tab 키를 누르면 포커스가 드롭다운 바깥으로 나가는 대신 첫 번째 게임 옵션(`role="button" tabindex="0"`)으로 들어가 버립니다. `closeDropdowns()`가 `<svelte:window on:click>`에만 걸려 있고 keydown 경로가 없기 때문입니다. 검색 결과가 여러 개면 키보드 사용자는 각 옵션을 하나씩 Tab으로 지나야 다음 필드에 도달합니다.
- **Fix**: `#gameSearch`에 `on:keydown`으로 Tab/Escape 시 `partyGameDropdownOpen = false` 처리 추가. 이상적으로는 `role="listbox"` + `aria-expanded` + 화살표 키 네비게이션까지 포함한 콤보박스 패턴으로 전환.
- **Command**: `$impeccable harden`

**[P2] 고정팟 생성/수정 폼, 제출 중 로딩 표시 없음 → 중복 제출 위험**
- **왜 문제인가**: 1.5초 네트워크 지연을 주입해 "만들기" 클릭 직후 버튼 상태를 확인한 결과, 응답이 오기 전까지 버튼이 계속 활성 상태였습니다(`disabledDuring: false`). 느린 네트워크에서 재클릭하면 동일 고정팟이 두 번 생성될 실질적 위험이 있습니다.
- **Fix**: `use:enhance` 콜백 시작 시 로컬 `isSubmitting` 플래그로 버튼 `disabled` + "만드는 중…" 텍스트 전환.
- **Command**: `$impeccable polish`

**[P2] 홈페이지의 동명 `.btn-danger`가 새 토큰(`--status-danger-bg`)으로 이관되지 않음**
- **왜 문제인가**: `src/routes/+page.svelte:3816,3825`가 여전히 `--color-red-dark`를 배경으로 씁니다. 현재는 텍스트 색도 `--bg-primary`로 같이 뒤집혀서 우연히 안전하지만(라이트 4.98:1, 다크 6.23:1), 이건 설계가 아니라 우연입니다. `--bg-primary`가 나중에 다른 다크 회색으로 조정되는 순간 이번에 마이페이지에서 고친 것과 똑같은 앨리어싱 버그가 홈페이지에서 재발합니다.
- **Fix**: 홈페이지 `.btn-danger`도 `--status-danger-bg`로 통일.
- **Command**: `$impeccable harden`

**[P3] 다크 테마에서 빈 상태 안내 문구 저대비 (3.56:1)**
- **왜 문제인가**: `.empty-state-small`/`.empty-titles`가 `--text-muted`(#6b7280) on 다크 배경(#1a1b1e)으로 AA 미달. 이번 라운드 변경사항과는 무관해 보이나 처음 잡힌 항목입니다.
- **Fix**: 다크 테마의 `--text-muted` 톤을 살짝 밝혀 4.5:1을 확보.
- **Command**: `$impeccable harden`

## Questions to Consider

1. 게임/멤버 검색 드롭다운을 진짜 ARIA 콤보박스 패턴(화살표 키 이동, Escape로 닫기, Tab은 다음 필드로)으로 통일하면, "마우스는 되는데 키보드는 안 되는" 절반짜리 수정이 반복되는 걸 구조적으로 막을 수 있지 않을까요?
2. "+N명 더 보기"처럼 자기 자신을 DOM에서 제거하는 버튼에는 포커스 이동을 명시적으로 처리하는 게 이 페이지의 일반 규칙이 되어야 하지 않을까요 — 비슷한 패턴(칭호 해제, 파티 삭제 후 목록 갱신 등)이 이 파일에 더 있을 수 있습니다.
3. `--status-danger-bg` 같은 의미 기반 토큰을 새로 만들 때마다 기존 `--color-red-dark`/`--color-red` 사용처를 전수 grep해서 마이그레이션 체크리스트로 남기면, 홈페이지의 우연한 안전 상태에 의존하지 않아도 되지 않을까요?
