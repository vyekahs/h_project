## 핵심 규칙

**기획서 본문에 코드 블록(``` ```) 절대 금지.**

코드 대신 자연어로 기능, 동작, 규칙을 설명한다. 기술적 고려사항은 문서 끝의 별도 섹션에만 기재.

## 기획서 구성

### 1. 개요
- 무엇을 만드는지 한 줄 요약
- 왜 만드는지 (배경/동기)
- 목표 사용자

### 2. 핵심 기능
- 주요 기능을 불릿 리스트로 나열
- 각 기능의 동작을 자연어로 설명
- 우선순위가 있다면 명시 (MVP / 후순위)

### 3. 유저 플로우
- 사용자 관점에서 단계별 흐름을 텍스트로 서술
- "사용자가 ~ 하면, ~ 가 표시된다" 형식
- 분기가 있으면 조건별로 나누어 설명

### 4. 화면 구성
- 각 화면/뷰를 텍스트로 설명
- 화면에 포함되는 요소 나열 (버튼, 입력 필드, 표시 영역 등)
- 레이아웃은 "상단에 ~, 중앙에 ~, 하단에 ~" 식으로 서술
- 필요 시 ASCII 레이아웃 스케치 가능 (코드 블록 아닌 텍스트)

### 5. 규칙 / 로직
- 게임 규칙, 비즈니스 로직 등을 자연어 규칙으로 서술
- "~ 일 때 ~ 한다", "~ 는 ~ 보다 우선한다" 형식
- 숫자/공식이 필요하면 인라인으로 표기 (코드 블록 아님)

### 6. 엣지 케이스
- 예외 상황과 그때의 동작을 나열
- "만약 ~ 라면 ~ 처리한다"

## 기술 참고

> 이 섹션만 기술적 고려사항을 기재할 수 있다.

기획 본문과 분리된 별도 섹션. 아래 내용을 간결하게 기재:
- 필요한 데이터 구조 (텍스트 설명 위주)
- 기존 코드에서 재사용할 수 있는 부분 참고
- API 설계 시 엔드포인트/파라미터 참고
- 성능/기술적 제약사항

이 섹션에서도 코드 블록은 최소화. 꼭 필요한 경우만 간단한 의사코드 허용.

## 작성 스타일

- **불릿 포인트 위주** — 장문의 문단 지양
- **자연어 규칙** — "X는 Y를 한다" 형식으로 명확하게
- **구체적 수치** — "약 3초" 대신 "3초", 모호한 표현 지양
- **짧고 명확하게** — 한 항목에 한 가지 내용만
- **코드 NO** — 구현은 기획 승인 후 별도 진행

## 하지 말 것

- 코드 블록으로 구현 예시 작성
- 컴포넌트 구조나 파일 구조 제안
- 타입 정의나 인터페이스 작성
- "이렇게 구현할 수 있습니다" 식의 코드 제안
- 기획 단계에서 기술 스택 결정
